# TASK-66: API сводок, кеш, актуальность и лимиты

- **ID:** `TASK-66`
- **Блок:** 10. ИИ-сводки с проверяемыми наблюдениями
- **Статус:** Реализовано; автоматические проверки выполнены
- **Приоритет:** Высокий (P1)
- **Зависимости:** `TASK-62`, `TASK-63`, `TASK-64`, `TASK-65`

## Цель

Связать выборку, расчёт, генерацию и публикацию в единый серверный поток. Одинаковые данные должны использовать один результат, а редактирование задачи не должно немедленно вызывать LLM.

## Объём работ

- Добавить авторизованные API: получение фактических данных/последнего отчёта по периоду, архив с пагинацией, чтение отчёта, запрос генерации и статус задания. Зафиксировать точные пути в OpenAPI; асинхронная новая генерация возвращает 202 и job ID, совпавший кеш — готовый отчёт.
- Клиент отправляет параметры периода и фильтры; backend получает записи по серверной сессии. Не принимать owner ID или готовые пользовательские метрики как источник истины.
- Один worker строит согласованный снимок, факты и payload, вызывает модель, проверяет ответ и атомарно публикует версию. Фактические данные доступны до готовности LLM.
- Вычислять стабильный fingerprint по всему релевантному набору и фактам: учитывать добавление/удаление, смену статуса, содержание, чек-лист, теги, даты, сравнение, версии генератора. Одного `updatedAt` недостаточно, в частности для массового изменения фокуса.
- Отделить изменение данных от течения времени: переход срока/дня, сдвиг rolling-периода и сравнения обновляют актуальность. Не включать каждую секунду `now` в кеш-ключ; определить дискретные временные основания и ближайший момент смены факта.
- Перед генерацией сверять актуальность в БД; GET и открытие страницы сами не вызывают LLM. Изменение записи только инвалидирует/выявляет устаревание, без генерации на каждое нажатие.
- Повторный ручной и автоматический запрос одинакового входа объединяются одним заданием. «Обновить» не обходит дедупликацию, лимиты и бюджет.
- Если данные изменились во время запроса, опубликованный снимок содержит исходный `asOf` и помечается stale; не подписывать его актуальным.
- Добавить серверные ограничения частоты, входного/выходного бюджета и параллельности по владельцу/системе. Ошибки и retry ограничены; фронтенд cooldown не является защитой сервера.
- При пустом периоде возвращать фактический пустой отчёт без вызова модели. При ошибке модели сохранять успешную версию и предоставлять фактический fallback с отдельным признаком режима.
- Исторические отчёты не пересчитывать молча; явный пересчёт создаёт новую версию с оговоркой о текущем состоянии источников.

## Критерии приёмки

- Повтор одного входа не тратит второй запрос; независимые владельцы не разделяют кеш.
- Появление просрочки без редактирования записи и удаление исходника обнаруживаются.
- Старый успех остаётся доступен при failed refresh; пустая статистика не подменяет ошибку чтения БД.
- API не редактирует пользовательские задачи по рекомендации модели.

## Проверки

- Интеграционные тесты cache hit/miss, конкурентных запросов, изменения данных во время генерации, времени, лимитов и недоступности БД/провайдера.
