# TASK-46: Аутентификация и идентичность клиента

- **ID:** `TASK-46`
- **Блок:** 9. Облачный backend и ИИ-обработка ввода
- **Статус:** Реализовано; автоматические проверки пройдены
- **Приоритет:** Критический (P0)
- **Зависимости:** `TASK-45`, `TASK-45A`

## Цель

Идентифицировать пользователя на backend и обеспечить одинаковую авторизацию для веб- и будущих Expo-клиентов.

## Контекст и связанные части проекта

В проекте пока нет учётных записей или серверной авторизации. Записи должны принадлежать конкретному клиенту; доверять переданному браузером `ownerId` нельзя.

## Объём работ

- Добавить PostgreSQL-миграции для пользователей и серверных сессий; регистрация и вход выполняются через Node API по email/паролю.
- Хешировать пароли через `crypto.scrypt` с уникальной солью; сравнивать хеши через `crypto.timingSafeEqual`. Ограничить частоту регистрации и входа.
- Выдавать короткоживущий JWT access token и случайный refresh token; хранить в базе только хеш refresh token. Реализовать ротацию, отзыв при выходе и обнаружение повторного использования старого refresh token.
- Реализовать middleware Node API для проверки подписи, срока, issuer/audience токена и получения текущего пользователя.
- Определить endpoints регистрации, входа, обновления сессии, выхода и текущего профиля. Для веба refresh token хранится в HttpOnly cookie (Secure в production), для Expo — в защищённом хранилище платформы; обновление через cookie защищено от CSRF и проверяет Origin.
- Защитить пользовательские endpoints; принимать владельца записи только из проверенного токена.
- Определить минимальный профиль клиента и формат ответа о текущей сессии для разных платформ.
- Ключ подписи JWT и credentials базы хранить только на сервере; не включать пароли и токены в логи или ответы профиля.

## Критерии приёмки

- Защищённый endpoint возвращает пользователя с валидным токеном и `401` без токена или при неверной подписи/истёкшем токене.
- Клиент не может передать другой `ownerId` и прочитать или изменить чужие данные.
- Auth-контракт описан так, чтобы веб и Expo могли передавать один и тот же bearer token.
- Выход отзывает refresh-сессию; повторное использование отозванного/заменённого refresh token отклоняется. Пароли и исходные refresh tokens не хранятся в базе.

## Проверки

- Тесты валидного, отсутствующего, истёкшего и поддельного токена.
- Интеграционные проверки регистрации, входа, ротации/отзыва сессии, rate limit и CSRF для веб-cookie.
- Проверка двух пользователей на отдельной тестовой PostgreSQL-базе.
