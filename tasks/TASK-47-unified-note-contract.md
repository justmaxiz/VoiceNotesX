# TASK-47: Единая модель заметки и API-контракт

- **ID:** `TASK-47`
- **Блок:** 9. Облачный backend и ИИ-обработка ввода
- **Статус:** Реализовано; автоматические проверки пройдены
- **Приоритет:** Критический (P0)
- **Зависимости:** Нет

## Цель

Определить один переносимый контракт записи, в котором заметка может иметь расписание, а AI не выбирает отдельный тип «задача/заметка».

## Контекст и связанные части проекта

Сейчас `src/types/item.ts` содержит `Item.type: 'task' | 'note'`, а `src/types/ai.ts` и `src/lib/gemini.ts` требуют `entity_type`. Эти контракты используются календарём, Kanban, поиском, drawer и Quick Capture. Будущие Expo-клиенты должны использовать тот же JSON-контракт через backend.

## Объём работ

- Описать единую сущность `Note` и версионированные DTO для REST API; сохранить AI-поля `title`, `description`, `due_date`, `start_date`, `deadline`, `priority`, `category_tag`, `transcript_summary` и `checklist` там, где они применимы.
- Согласовать JSON response schema с TypeScript-контрактом, включая `start_date` и `deadline`, которых не хватает текущей схеме в `src/lib/gemini.ts`.
- Удалить `entity_type` из AI-результата: модель возвращает содержание и поля расписания, а не отдельный тип сущности.
- Зафиксировать единое правило представления: запись без выбранного расписания является заметкой; запись с датой и/или временем показывается в запланированных задачах/календаре. Это один объект и один ID во всех представлениях.
- Описать создание, изменение и снятие расписания, включая дату без времени, а также формат дат, часов и часового пояса.
- Опубликовать контракт в OpenAPI или эквивалентном машинно-читаемом описании, пригодном для Expo-клиента.

## Критерии приёмки

- Контракт не требует `entity_type` и не создаёт разные записи для заметки и задачи.
- В API-документации описаны обязательные/необязательные поля, даты без времени, ошибки валидации и версионирование.
- Одна и та же запись остаётся одной записью при добавлении или удалении расписания.

## Проверки

- Unit-тесты чистой функции определения представления по полям расписания, включая отсутствие расписания, только дату, время и очищение расписания.
- Проверка OpenAPI-схемы на согласованность с TypeScript DTO.
